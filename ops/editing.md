# 編集機能の公開と復旧

編集は Zaim へ保存した後、再取得・照合した明細を D1 へ反映する。
方式の理由は [ADR-0036](../docs/adr/0036-refresh-edited-mirror-with-shared-gate.md) と
[ADR-0037](../docs/adr/0037-foreground-edit-plans.md) を参照する。

## 公開前の確認

現時点のコード経路と fixture による検証は、実データでの確認とは区別する。
公式の更新 API ドキュメントは認証が必要で、2026-09-05 の読み取り調査では確認できていない。

| 項目 | 確認できていること | 公開前に残る確認 |
|---|---|---|
| 支出・収入の部分更新 | 2026-08-18 の実測で、金額の省略は 0、その他の指定省略は保持 | 今回の PUT 経路で指定値・空欄・未変更列を照合する |
| 支出の品名 | `receipt_id` を持つ支出で Zaim の品名欄が表示される | 今回のフォームからの変更と消去・復元 |
| 収入の品名 | API で更新できるという過去の記録はある | 収入画面の表示・編集・消去・復元を個別に確認する |
| 振替 | 一覧取得・表示の実装がある | 更新可能項目、両口座、残高、連携関係、非表示列への影響 |
| 文字数 | 入力上限はアプリ側の初期値 | 公式の更新時の上限と境界での実測 |
| 一括編集 | 対象固定と逐次処理を実装 | 初期上限の所要時間、iPhone の中断・復帰、Worker CPU・要求数 |

編集固有の入力上限と計画期限は [edit-contract.ts](../worker/src/edit-contract.ts)、
金額上限は [limits.ts](../worker/src/limits.ts) を参照する。
金融機関連携の明細が API に返らない制約は [#33](https://github.com/Ries630/ZaimViewer/issues/33) を参照する。

## 検証と有効化の順序

1. ローカルの fixture を使い、単体編集・一括編集・失敗・再照合を確認する。
2. 読み取り専用の Preview を公開し、レイアウトと既存の閲覧機能を確認する。
3. 実データ検証の対象 ID、確認時の全列、変更する項目と値、復元値、実行回数を具体化して承認を得る。
   明細の新規作成や削除が必要なら、それも承認対象に含める。
4. 同期の旧プロセスが動いていないことを確認し、共通排他に対応した同期スクリプトへ切り替える。
   launchd が参照するチェックアウトも確認する。旧版の同期が残っている間は編集を有効化しない。
5. Worker に Zaim の認証情報を登録し、承認された種別だけを有効化する。
6. 検証対象で単体編集、Zaim からの再取得、D1、iPhone 表示を照合し、指定した値へ復元する。
7. 承認された少数の対象で一括編集と復元を行う。通信切断時には再送前に結果を照合する。
8. 結果を [#72](https://github.com/Ries630/ZaimViewer/issues/72) へ記録し、確認できた能力のみ公開する。

本番と Preview は同じ D1 を参照する。Preview URL であっても保存は実データの更新になる。
Secret の登録や本番デプロイを含む公開操作は、準備した差分と検証対象を確認してから行う。

## 設定

| 名前 | 用途 |
|---|---|
| `EDIT_ENABLED` | `true` の場合に編集計画の作成と新規実行を有効化する。既定は無効 |
| `EDIT_VERIFIED_MODES` | 確認した種別をカンマ区切りで指定する |
| `EDIT_INCOME_NAME_VERIFIED` | 収入の品名を実機で確認した場合のみ `true` |
| `EDIT_TRANSFER_VERIFIED` | 振替の更新を実機で確認した場合のみ `true` |

設定の解釈は [edit-config.ts](../worker/src/edit-config.ts) が担う。
ローカル設定は `.dev.vars`、公開設定は `wrangler.jsonc` の `vars` に置く。
四つの Zaim 認証情報の名前は [.dev.vars.example](../.dev.vars.example) を参照し、
Worker には `wrangler secret put <NAME>` で登録する。値を Issue、ログ、設定ファイルへ転記しない。

## 保存が途中で止まったとき

画面に保存した計画を再表示する。成功済みは再送せず、未実行は利用者が再開するまで送らない。
「結果未確認」「ミラー反映待ち」は照合を実行する。照合は Zaim の読み取りとミラーの修復を行い、
Zaim の更新要求を再送しない。変更値と未変更列が一致しなければ、自動で未実行状態へ戻さない。

計画の期限は新規実行の可否にだけ適用する。期限切れ後も、保存済みの計画の照合は可能。
未確認の結果が残る計画は削除しない。現在は自動削除を行わず、保持容量を運用で確認する。
計画を削除する場合はすべての結果が確定済みであることを確認し、実行 ID を指定して別途承認を得る。

確認画面から入力へ戻った場合、未実行の計画が D1 に残る。これらは実行期限の経過後、
全項目が `pending` で外部送信歴がなく、対応するゲート処理もないことを確認したうえで、
対象の計画 ID を指定して別途承認を得て削除できる。

## 強制終了で排他が残ったとき

通常の例外では処理が排他を解除する。Worker の強制終了、端末停止、同期プロセスの強制終了では
所有者が残り、後続の保存・同期を止める。読み取りは継続できる。

1. 編集を無効にし、同期の新規起動を止める。
2. `mutation_gate` の所有者 ID・種別・開始時刻を読む。認証値や明細の原文をログへ出さない。
3. 該当する Worker 要求や同期プロセスが終了していることを確認する。経過時間だけで判断しない。
4. 該当計画の状態を確認する。`sending` は外部更新の可能性があるため未確認として扱う。
5. 解除対象の所有者 ID と理由を提示して承認を得る。所有者 ID が一致する行だけを条件付きで削除する。
   無条件削除や別所有者への上書きを行わない。
6. 該当計画を再照合する。値が一致しない場合は新しい編集や同期を開始せず、Zaim の最新値と
   元の値・変更予定値を比較して修復方法を決める。
7. 未確認結果がなくなったことを確認してから同期と編集を再開する。

Zaim と D1 は一つのトランザクションにはならないため、外部処理の結果が不明な状態からの
自動再送や自動ロールバックは行わない。
