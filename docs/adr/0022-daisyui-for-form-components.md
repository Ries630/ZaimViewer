# ADR-0022: DaisyUI を採用し、色は semantic トークンで書く

- ステータス: 承認済み
- 日付: 2026-08-12
- 関連: [#15](https://github.com/Ries630/ZaimViewer/issues/15)、[#14](https://github.com/Ries630/ZaimViewer/issues/14)、[ADR-0021](0021-no-list-virtualization.md)

## 背景

[#14](https://github.com/Ries630/ZaimViewer/issues/14) で明細一覧まで作った時点で、
クライアントには**フォーム部品が 1 つも無い**。`src/components/` にあるのは一覧・
サマリ・同期の鮮度表示だけで、入力欄・選択・トグルはこれから
[#15](https://github.com/Ries630/ZaimViewer/issues/15) のフィルタパネルで一気に増える
（期間 2 つ・モード 3 つ・カテゴリ 46・ジャンル 129・口座 36・金額 2 つ・キーワード・
店名の除外）。判断が必要なのはここで、一覧の見た目ではない。

もう 1 つ、[#18](https://github.com/Ries630/ZaimViewer/pull/18) で表示をライトに固定した
（端末がダークモードだと本文が黒地になり金額が読めなかった）。そのとき
ダークモードの入れ方を「DaisyUI の採否を決めてから」と保留してある。素の Tailwind で
`dark:` を全コンポーネントに撒くと、テーマ機構に載せ替えるとき無駄になるため。

決めるために、捨てブランチ `spike/daisyui` に `/mock` を作り、**同じ中身の
フィルタパネルを素の Tailwind 版と DaisyUI 版で並べた**。項目・状態・バリデーションは
共通のフックに置き、差が見た目だけになるようにしてある。選択肢はローカル D1 の
実データ（カテゴリ 46 / ジャンル 129 / 口座 36）。iPhone Safari で見比べた。

測った値は以下。

| 観測 | 素の Tailwind | DaisyUI 5.7.16 |
|---|---|---|
| パネルの行数 | 273 | 232 |
| `className` の総文字数 | 2,134 | 1,768 |
| 自前で持つクラス定義 | 5 定数（`INPUT` / `CHIP` / `CHIP_ON` / `CHIP_OFF` / `LEGEND`） | 0 |
| ビルド後の CSS（同一ソースで比較） | 16.82 kB / gzip 4.38 kB | 63.89 kB / gzip 11.81 kB |

作業中に踏んだことが 2 つある。

- **DaisyUI の `.select` は `<select multiple>` を壊す。** `.select[multiple]` の
  指定はあるが `display: inline-flex` が残るため option が flex item になり、
  文字が重なって描かれる。高さ指定の有無に関係なく再現した（5.7.16）
- **DaisyUI の base スタイルは既存の一覧の見た目を変えなかった。** 同じブランチで
  `/` を描いて確認した。配色も字送りも #14 のまま

テーマ色を変える手間も測った。組み込みの `light` を名前で拾って
`--color-primary` と `--color-primary-content` だけ上書きする **CSS 8 行**で、
DaisyUI パネルの primary が既定の紫から sky-600 に変わる。**JSX の変更はゼロ。**

ただしこれが効くのは semantic な色名（`primary` / `base-100` / `base-content`）で
書いた部分だけで、`text-gray-500` のようなパレット直書きはどのテーマでも同じ色の
ままになる。現状のパレット直書きは **22 箇所 / 5 ファイル**（`TransactionRow` 7、
`TransactionList` 7、`SyncFreshness` 4、`SummaryBar` 2、`App` 2）。

## 決定

DaisyUI 5 を採用する。あわせて次の 3 つを決めた。

1. **色は DaisyUI の semantic トークンで書く**（`text-base-content/60` など）。
   パレット直書き（`text-gray-500`）はテーマから外れるので使わない
2. **既存の 22 箇所も DaisyUI 導入 PR で置き換える。** #15 に入る前にテーマ機構へ
   乗り切り、「新しいコードだけ semantic」という二重状態を残さない
3. **色の値そのものは今決めない。** 組み込み `light` の既定（primary は紫）のまま
   進める。上のとおり後から CSS 8 行で変えられる

テーマは light 固定のまま。ダークモードはこの ADR では決めない。

## 検討した代替

- **素の Tailwind でフォーム部品を自前で書く** — 行数もクラス量も僅差
  （273 対 232 行）で、CSS は 47 kB 小さい。落としたのは、5 つのクラス定数が
  示すとおり**自前のミニ design system を持ち続けることになる**ため。それを持つ
  なら、ダークモードを入れるときに `dark:` を全箇所に撒くか、結局テーマ変数を
  自前で定義するかのどちらかになる。CSS 47 kB（gzip 7.4 kB）はその代償として
  安いと判断した
- **DaisyUI をフォーム部品にだけ使い、既存の一覧はパレット直書きのまま残す** —
  置き換えの手間は消えるが、テーマが効く範囲と効かない範囲が画面の中で混ざる。
  ダークモードを入れる判断が実質できなくなるので落とした

比較したのはこの 2 案だけで、**他の UI ライブラリ（shadcn/ui、Radix、Park UI など）は
検討していない**（未検討）。Tailwind v4 に CSS 側の `@plugin` だけで載り、設定ファイルを
増やさない点が既存の方針と合っていたため、DaisyUI を最初の候補として試した。

## 結果

- **CSS が 47 kB（gzip 7.4 kB）増える。** 現状 gzip 11.81 kB
- **`<select multiple>` を DaisyUI の見た目では使えない。** 複数選択はチップ
  （`<input type="checkbox" class="btn">`）で組むことになる。#15 の口座 36 件・
  カテゴリ 46 件はこの形に固定される
- **後から色を変えられる範囲は、semantic で書いた部分と正確に一致する。**
  パレット直書きを 1 箇所でも足すと、そこだけテーマから取り残される。
  これは lint では防げず、レビューで見るしかない
- **見た目が DaisyUI のクラス名に結びつく。** 外すとなれば全コンポーネントの
  書き換えになる。#14 の一覧を含めてテーマ機構に載せる決定なので、
  戻り道は入れる前より狭い
- 既存 22 箇所の置き換えでグレーの段階などが微妙に変わる。**実機で見直しが要る**

## 再評価のサイン

- **フォーム部品以外で DaisyUI をほとんど使っていないと分かったとき。** #15 が
  終わった時点で使っているクラスを数える。フォームだけなら、自前でも足りた
  ことになるので上の判断は間違っていたことになる
- **DaisyUI が Tailwind の次のメジャーに追随しなくなったとき。** 採用理由の
  ひとつが「CSS 側の `@plugin` だけで載る」ことなので、そこが崩れたら見直す
- CSS の増分が問題になったとき（今は gzip 11.81 kB）
- ダークモードを入れる判断をするとき。semantic トークンで書き切れているかが
  そこで試される
