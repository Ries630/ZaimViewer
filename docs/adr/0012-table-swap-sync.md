# ADR-0012: 同期は `*_new` テーブルへ構築し `batch()` で差し替える

- ステータス: 承認済み
- 日付: 2026-08-07
- 関連: `11ba2a6`、`07bd63d`、[ADR-0007](0007-atomic-swap-sync.md) を置換

## 背景

[ADR-0007](0007-atomic-swap-sync.md) の「全件構築 → 検証 → アトミックに差し替え」
という意図は変えたくない。同期の失敗で空のミラーが残るのは、認証切れと
区別が付かず最悪の壊れ方をする。

しかし [ADR-0010](0010-d1-as-mirror.md) で D1 に移り、**ファイル差し替えに
相当する操作が無くなった**。`os.replace` の代わりが要る。

D1 の `batch()` は複数ステートメントを単一トランザクションとして実行する。
これが本当にロールバックするかは、故意に失敗させて確認した（`11ba2a6`）。

## 決定

同期は `transactions_new` のような `*_new` テーブルに全件を構築し、
`DROP` → `RENAME` → インデックス再作成を単一の `batch()` で実行して差し替える。
認証確認と 0 件チェックは差し替えより**前**に置く。

## 検討した代替

- **既存テーブルを DELETE してから INSERT** — 同期の全所要時間（約 17 秒）に
  わたって中途半端な状態が読まれうる
- **D1 の Time Travel に頼る** — 壊れてから戻す仕組みであって、壊れないための
  仕組みではない。読み手が壊れた状態を見る問題は解決しない

## 結果

- 途中で失敗すれば旧テーブルがそのまま残る（故意に失敗させて検証済み）
- 差し替えに必要なのは 13 文だけで、1 バッチに収まる。
  **これが [ADR-0015](0015-sync-outside-worker.md) を成立させている。**
  `*_new` への一括投入は多数のリクエストに分かれてよい（誰も読んでいない
  テーブルなので原子性が要らない）
- テーブル名が動的になるため、Drizzle のスキーマでは表現できない。
  同期側が素の SQL のままなのはこれが理由（[ADR-0014](0014-drizzle-for-reads.md)）
- **本番 D1 での `batch()` ロールバックは未確認。** ローカルは miniflare の
  SQLite なので、実 D1 での挙動は初回デプロイ後に確認する
  （[#2](https://github.com/Ries630/ZaimViewer/issues/2)）
- 差し替え時に一瞬だけテーブルが存在しない窓がある。`batch()` の
  トランザクション内なので読み手には見えないはずだが、上と同じく本番で確認が要る
