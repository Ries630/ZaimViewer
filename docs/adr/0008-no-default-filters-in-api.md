# ADR-0008: API にフィルタの既定値を持たせない

- ステータス: 承認済み
- 日付: 2026-08-06
- 関連: `5c2ea5f`、`worker/src/queries.ts`、[#4](https://github.com/Ries630/ZaimViewer/issues/4)

## 背景

普段見たい一覧には決まった前提がある。振替は除く、未来分（繰り返し登録の家賃で
2029 年まで入っている）は隠す、少額のノイズは隠す。実データではこの 3 段で
4,362 件 → 3,873 → 3,833 → 1,875 と絞れる。

この「普段の前提」を API の既定値にするかどうか。既定にすれば PWA は
パラメータを何も付けずに正しい一覧を得られる。

## 決定

API は「指定なし = 制限なし」に徹する。既定のフィルタは PWA 側が組み立てて
明示的に送る。

## 検討した代替

- **API 側に既定値を持たせる**（`exclude_transfer=true` を既定にするなど）— 楽だが、
  **「全件見たい」ときの外し方が分からなくなる。** `exclude_transfer=false` と
  書けばよいと知っている必要があり、それは API の応答からは読めない。
  また、curl や別のクライアントから叩いたときに件数が合わず驚く。
  暗黙の既定は、それを知らない読み手に対して嘘をつく

## 結果

- PWA は毎回フィルタを組み立てて送る必要がある。既定値の管理が PWA 側の責務になる
- API の応答が引数だけで決まる。件数が合わないときの調査先が 1 か所に絞れる
- 将来「よく使う除外条件に名前を付ける」プリセット層を載せる場合、その層は
  `TransactionFilter` を組み立てるだけでよく、SQL を書かずに済む
  （組み立ては `worker/src/queries.ts` に閉じている）

## 再評価のサイン

- PWA 以外のクライアントが増え、どれも同じ既定を再実装しているとき。
  その場合は API に既定を埋めるのではなく、プリセット層を明示的なパラメータとして足す
