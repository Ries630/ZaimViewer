# ADR-0035: `receipt_id` による品目化は支出だけに限定する

- ステータス: 承認済み
- 日付: 2026-09-02
- 関連: [#37](https://github.com/Ries630/ZaimViewer/issues/37)、[ADR-0003](0003-edit-through-zaim-api.md)、[ADR-0030](0030-receipt-id-gates-name-editing.md)

## 背景

[ADR-0030](0030-receipt-id-gates-name-editing.md) では、支出の編集画面（Payment detail）で
`receipt_id != 0` のときだけ品名欄が出る実機確認を、収入にも一般化した。その結果、
Issue #37 の固定計画に支出 1,080 件と収入 60 件を含め、2026-09-02 に全 1,140 件へ
`receipt_id` を後付けした。

支出は Zaim で品名ありになったことを実機で確認できた。一方、収入には支出のような
「品目なし / 品目入力」の切替がなく、`receipt_id` によって画面が変わるかは確認して
いなかった。実データでも、独自採番域を適用する前から `receipt_id != 0` だった明細は
支出 132 件、収入 0 件だった。現在 `receipt_id != 0` の収入 60 件は、すべて Issue #37 で
後付けした値である。

適用後の収入 60 件を適用前のミラーと比較すると、`receipt_id` と既知のタグ補正を除く
列に差分はなかった。データ破損は見つからなかったが、収入への後付けには確認済みの
効果がなく、未文書パラメータへ依存する理由もない。

## 決定

**`receipt_id` による品目化は支出だけに限定する。** Issue #37 で後付けした支出
1,080 件の値は維持し、収入 60 件の値だけを元の `receipt_id = 0` へ戻す。
復元には適用時と同じ固定計画を使い、計画値が付いた収入だけを更新する。支出や計画外の
値は変更しない。

今後、外部データから明細を移行するときは次の規則を使う。

- 支出で、移行元の商品名・品目名を `name` に保存する場合だけ、一意な `receipt_id` を採番する
- 支出でも、移行元の名称を店舗名として `place` にだけ保存する場合は採番しない
- 収入と振替には独自の `receipt_id` を採番しない

Issue #37 の固定計画は、誤って適用した収入を安全に特定して戻すため、支出と収入を含む
version 1 のまま保持する。ただし、適用と canary は支出だけを処理し、収入の復元は専用の
`--rollback-income` で行う。この固定計画を今後の移行対象の選択には使わない。

収入の `name` を将来の編集機能でどう扱うかは、`receipt_id` から推測せず、収入画面と
更新 API の挙動を別途検証して決める。

## 検討した代替

- **収入 60 件の値をそのまま残す** — 現状の画面で問題が見えない利点はある。落としたのは、
  確認済みの効果がないまま未文書パラメータへ依存し、`receipt_id` の意味を収入にまで
  広げることになるため
- **支出を含む 1,140 件をすべて戻す** — 独自採番を完全に取り除ける。落としたのは、
  支出では品名欄が出る効果を実機で確認済みで、Issue #37 の目的を失うため
- **収入を削除して作り直す** — `receipt_id` は戻せるが、明細 ID や作成日時を変える。
  in-place の PUT で 0 に戻せるため採用する理由がない

## 受け入れた代償

- `name` と `receipt_id` の関係を全明細種別で一律に扱えず、支出と収入で判断が分かれる
- 歴史的な固定計画には、現在は適用対象でない収入 60 件も復元用の対応表として残る
- 収入の品名表示・編集可否は、この ADR では確定しない

## 再評価の条件

- Zaim の収入画面で `receipt_id` による表示・編集の差が実機確認できたとき
- Zaim が収入にも品目入力を追加したとき
- Zaim の公開 API が `receipt_id` の意味と更新方法を文書化したとき
