# ADR-0026: フィルタの既定値と保存先を PWA が持ち、localStorage に永続化する

- ステータス: 承認済み
- 日付: 2026-08-13
- 関連: [#15](https://github.com/Ries630/ZaimViewer/issues/15)、[ADR-0008](0008-no-default-filters-in-api.md)（既定値を API に持たせない）、[ADR-0002](0002-no-local-only-data.md)（ローカル独自データを持たない）

## 背景

API は「指定なし = 制限なし」に徹しており（ADR-0008）、既定値は持たない。したがって
「振替を除外」「今日以前だけ」といった既定は PWA 側で組み立てる必要がある。
#14 の時点では `NO_FILTER = {}` を渡していたため、全 4,370 件が対象で、一覧の先頭は
2029-12 までの家賃（繰り返し登録）で埋まっていた。

本番データでの絞り込みの効き方（実測、2026-08-13 時点の 4,370 件）。

| 条件 | 件数 |
|---|---|
| 全件 | 4,370 |
| 振替を除外 | 3,879 |
| + 未来分を隠す | 3,839 |
| + 1,000 円未満を除外 | **1,881** |

フィルタは 8 項目あり、iPhone（390pt 幅）では一覧と同時には出せない。

## 決定

1. **既定は上の 3 段すべて。** `src/lib/filter.ts` の `DEFAULT_FILTER` に置き、
   初期表示は 1,881 件から始める
2. **状態は localStorage に永続化する**（キー `zaimviewer.filter.v1`）。
   URL のクエリとは同期しない
3. **復元は項目ごとに検証し、読めない項目だけ既定に倒す。** 丸ごと捨てない
4. **UI は「ヘッダ常設 + ボトムシート」。** キーワード欄と適用中のバッジをヘッダに
   常設し、残りはシートに入れる。シート内の変更は即座に反映し、下端のボタンは
   件数を出して閉じるだけにする（「適用」で確定させない）

## 検討した代替

### 既定値の範囲

- **振替除外 + 未来を隠す の 2 段まで（1,000 円は既定にしない）** — この 2 つは
  「見たいものが構造的に埋もれる」問題への対処で失う情報が無いのに対し、金額の下限は
  情報を落とす判断で、いくらで切るかは実データを触りながら決まる。`worker/src/queries.ts`
  にプリセット層を今作らない理由と同じ筋。落としたのは、3 段目まで入れて初めて
  「自動連携の細かな履歴が埋もれる」という #4 の完了条件に届くため。閾値が固まって
  いないことは認めたうえで、既定として置いて実データで確かめる側を選んだ
- **既定なし（ADR-0008 を UI にも徹底する）** — 一貫はする。落としたのは、起動のたびに
  未来の家賃が先頭に並ぶ画面になり、閲覧層として使えないため

### 保存先

- **URL のクエリと同期する** — 戻る操作で条件が戻り、リンクで共有できる。落としたのは
  主な入口がホーム画面から起動する standalone の PWA で、URL バーが見えず共有もしない
  ため。React Router は入っておらず、`history.replaceState` を自前で書くコストに
  見合わない
- **保存しない（`useState` のみ）** — 最も単純。落としたのは、iPhone で毎回同じ除外を
  組み直す手間が残るため
- **ミラー DB に保存する** — ADR-0002 の「ローカル独自データを持たない」に正面から
  反する。なお localStorage のフィルタ状態は明細の行に紐付くデータではないので、
  ADR-0002 には触れないと判断した

### 復元の壊れ方

- **JSON として読めなければ丸ごと既定に倒す** — 実装が短い。落としたのは、保存形式に
  項目を 1 つ足すたびに利用者の設定が消えるため。項目ごとに検証すれば、知らない項目は
  無視し、欠けた項目だけ既定になる
- **zod で検証する** — プロジェクトの入力検証は zod で揃えている。落としたのは、
  localStorage の 1 か所のためにクライアントのバンドルへ載せる価値が無いため
  （ADR-0025 で polyfill 19.86 kB を足した直後でもある）。手書きの型ガードは約 40 行

### UI の形

- **インライン展開（collapse）** — 実装が最も軽い。落としたのは iPhone の縦幅で
  8 項目を展開すると一覧がほぼ見えなくなるため
- **全画面モーダル** — 縦の余裕は最大。落としたのは一覧が完全に隠れ、条件をいじりながら
  結果の変化を確かめる使い方ができないため（件数だけが手がかりになる）
- **ドロワー（横から）** — iPhone では横幅が狭く、選択肢の一覧が窮屈になる

## 結果

- **初期表示から 1,000 円未満の明細が消える。** 手数料・少額のサブスクなど、少額でも
  見たいものはそのつど金額の下限を空にする操作が要る。「件数が合わない」と思ったとき、
  ヘッダのバッジを見れば理由は分かるが、操作は 1 手増える
- **端末をまたいで条件が引き継がれない。** localStorage なので、iPhone と Mac で
  別々の条件を持つ。共有もできない
- **条件をリンクで人に渡せない。** URL に出さないと決めたので、
  「この条件の一覧」を指す手段が無い
- **保存形式を変えるときは移行を考えることになる。** キーに `v1` を入れてあるが、
  項目ごとの検証で吸収しきれない変更（意味の変わる項目名の再利用など）が来たら、
  キーを上げて設定を捨てるか変換を書くかの判断が要る
- **シートを開いている間は一覧が backdrop の下に隠れる。** 件数（下端のボタン）でしか
  変化を確かめられない。インライン展開を落とした時点で受け入れた代償

## 再評価のサイン

- **1,000 円という閾値を触りたくなったとき。** 既定として妥当かを、そのときの
  実データの件数で測り直す
- **よく使う除外条件に名前を付けたくなったとき。** プリセット層を `TransactionFilter` を
  組み立てる層として載せる判断がそこで発生する（`worker/src/queries.ts` に SQL が
  閉じているので、その層は SQL を書かずに済む）
- **iPhone 以外からの閲覧が主になったとき。** URL 同期を落とした前提が崩れる
- **保存する項目が増えて、手書きの型ガードが見通せなくなったとき。** zod を落とした
  判断を、そのときのバンドルサイズと突き合わせ直す
