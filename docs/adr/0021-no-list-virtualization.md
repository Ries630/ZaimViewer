# ADR-0021: 明細一覧を仮想化せず、取得済みの全件を素の DOM で描く

- ステータス: 承認済み
- 日付: 2026-08-12
- 関連: [#14](https://github.com/Ries630/ZaimViewer/issues/14)、[#18](https://github.com/Ries630/ZaimViewer/pull/18)

## 背景

明細一覧は `useInfiniteQuery` で 100 件ずつ読み足していく。フィルタがまだ無い
（[ADR-0008](0008-no-default-filters-in-api.md) により API は既定値を持たず、
既定値を組み立てる [#15](https://github.com/Ries630/ZaimViewer/issues/15) は未着手）ため、
最後まで送ると本番の全 4,370 件が DOM に載る。主な入口は iPhone で、
「全件をスクロールして読める」ことが #14 の完了条件になっている。

実装してから測った。

| 観測 | 値 |
|---|---|
| 全件描画時の `<li>` | 4,370 |
| 全件描画時の DOM ノード総数 | 33,624 |
| JS ヒープ | 172MB |
| ページ全体の高さ | 362,385px |
| 全 44 ページの読み込み | 15 秒 |
| 全件描画した状態で 20 回スクロール + 強制レイアウト | 実質 0ms |

デスクトップ Chrome を 393×852 のモバイルビューポートで動かした値なので、
実機の代わりにはならない。そこで Preview URL（`wrangler versions upload`）を
iPhone の Safari で開いて確かめた。**末尾（2014-02）まで到達でき、
動作は軽快。ページの読み込み中に 0.2 秒ほど止まるが許容範囲**、というのが
実機での評価。

## 決定

仮想化ライブラリを入れず、取得済みの明細をそのまま DOM に並べる。

## 検討した代替

- **最初から `@tanstack/react-virtual` を入れる** — 依存が 1 つ増え、行の高さが
  可変（主表示・文脈・補足の 3 段のうち埋まっている段だけを出すので、行ごとに
  2 段だったり 3 段だったりする）ぶん実装も測定も重くなる。上の測定値に対して
  払う代償として見合わない。**測る前に入れると、入れた効果を確かめる基準も
  無くなる**

案はこの 1 つしか比較していない。ページサイズを増減させる案や、日付でページを
切る案は検討していない（未検討）。

## 結果

- **4,370 件を最後まで送ると 172MB のヒープを使う。** iPhone の Safari が
  メモリ逼迫でタブを破棄する余地が残る。今回の実機確認では起きなかったが、
  他のタブやアプリが多い状況までは試していない
- **一覧の途中に「行の高さが分かっている」前提の機能を後から足しにくくなる、
  ということは無い。** 仮想化を入れていないので、むしろ制約は少ない側にいる
- 逆に、将来仮想化を入れるときは行コンポーネントの高さを測る仕組みから
  作ることになる。今その準備をしていないぶん、そのときの作業は増える

## 再評価のサイン

- **フィルタ無しで全件を送るのが常態になったとき。** #15 の既定値
  （振替除外・未来分を隠す・1,000 円未満を除外）が入れば対象は 1,881 件まで減り、
  この判断の前提は緩む。逆に「全件を見る」使い方が主になるなら測り直す
- **件数が増えたとき。** 同期のたびに増える。1 万件を超えたら上の数字を取り直す
- 実機でタブが破棄される、またはスクロールが引っかかると感じるようになったとき
