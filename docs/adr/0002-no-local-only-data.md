# ADR-0002: ローカル独自データを持たず、除外はクエリのルールで表現する

- ステータス: 承認済み
- 日付: 2026-08-06
- 関連: `be3b40a`、[ADR-0008](0008-no-default-filters-in-api.md)

## 背景

除外したい明細には 2 種類ある。振替（`mode = 'transfer'`）と、自動連携で入る
細かなノイズ（少額の決済など）。実データでの内訳は、全 4,362 件のうち
振替が 489 件、1,000 円未満が振替・未来分を除いてなお 1,958 件だった。

これを「どう表現するか」で 2 通りある。行に印を付けるか、条件で表すか。

前提として、この閲覧層を作る動機のひとつは**「入力時に選別する」運用からの脱却**にある。
Zaim に入れる時点で仕分ける手間を減らしたいから、閲覧側で絞りたい。

## 決定

ミラー DB に独自のカラム（重要フラグ、メモ、除外フラグなど）を一切追加しない。
除外は `worker/src/queries.ts` が組み立てるクエリの条件として表現する。

## 検討した代替

- **除外フラグ列を持たせる** — 明細ごとに「これは見なくてよい」を記録する。
  一度付ければ確実に消える反面、**新しい明細が入るたびに付け続ける必要がある**。
  同期は毎回全件を入れ直すので、フラグを別テーブルに逃がして ID で結合する
  作りも要る。そして何より、これは「入力時に選別する」旧運用に名前を変えただけで、
  解こうとしていた問題そのものに戻る
- **Zaim 側のコメント欄を使う** — ローカルには持たないが、Zaim の全明細に
  手で書き込むことになり、手間は上と同じ

## 結果

- **この DB は使い捨てのミラーになる。** 壊れたら再同期すればよく、バックアップも
  マイグレーションも要らない。Zaim が唯一の正。これは以降の判断
  （[ADR-0004](0004-sqlite-as-mirror.md)、[ADR-0010](0010-d1-as-mirror.md)、
  [ADR-0012](0012-table-swap-sync.md)）すべての前提になっている
- 「この 1 件だけ例外的に隠す」ができない。ルールで表せない除外は表せない
- ルールは今後増える明細にも自動で効く。運用の手間が件数に比例しない

## 再評価のサイン

- ルールでは表せない一件物の除外が繰り返し必要になったとき。その場合でも、
  まず Zaim 側のデータを直す（[ADR-0003](0003-edit-through-zaim-api.md)）方向を先に試す
