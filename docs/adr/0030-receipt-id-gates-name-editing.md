# ADR-0030: 品名を編集できるのは `receipt_id` を持つ明細だけとし、持たない既存分には後付けする

- ステータス: 廃止（ADR-0035 により置換）
- 日付: 2026-08-19
- 関連: [#37](https://github.com/Ries630/ZaimViewer/issues/37)、[#6](https://github.com/Ries630/ZaimViewer/issues/6)、[ADR-0002](0002-no-local-only-data.md)、[ADR-0003](0003-edit-through-zaim-api.md)、[ADR-0029](0029-detail-bottom-sheet-as-edit-entry.md)

## 背景

Zaim には入力モード（品目なし / 品目入力）があり、品目入力で登録した明細だけが
`receipt_id` を持つ。ZaimViewer は品目を個別の明細として出すが、Zaim の画面では
同じ `receipt_id` の品目が合算された 1 明細として出る。

**`receipt_id` を持たない明細では、`name`（品名）が入っていても Zaim の UI が扱えない。**
iPhone 実機で確認した挙動:

| 画面 | `receipt_id = 0` かつ `name` あり |
|---|---|
| 履歴一覧 | 品名が出る |
| 詳細（History detail） | 出ない |
| 編集（Payment detail） | 欄そのものが無い |

編集画面に入力モードの切替は無く、品名欄の有無は明細の `receipt_id` だけで決まる。
作成時に決まった性質を UI から変える経路が無いため、この状態の明細は Zaim 上では
**恒久的に品名が読み取り専用**になる。

本番ミラー 4,370 件を数えたところ、この状態が **1,143 件**あった
（payment 1,080 / income 60 / transfer 3）。うち 895 件（78%）が `#かんたん家計簿` タグを持つ。
**Zaim 公式のかんたん家計簿取込が `receipt_id` を採番していない**ことに起因する。
発生は 2026-04-27 で止まっており（2026-05 に品目入力へ移行したため）、以降 1 件も増えていない。

`name` の有無では入力モードを判別できない。両方向に例外がある:

| | `name` 空 | `name` あり |
|---|---|---|
| `receipt_id = 0` | 3,113 | 1,143 |
| `receipt_id != 0` | 18 | 103 |

`receipt_id` を持つ側は 121 件 / 84 レシートで、内訳は 1 品 77・2 品 4・12 品 3。
同一 `receipt_id` のグループが日付・店舗・口座・mode で割れているものは 0 件だった。
ただし複数品の 7 グループのうち 2 グループはカテゴリとジャンルが混在している。

工程 ③（[#6](https://github.com/Ries630/ZaimViewer/issues/6)）の編集は Zaim の更新 API を
経由する（[ADR-0003](0003-edit-through-zaim-api.md)）。**この API は `receipt_id` の値に
関わらず `name` を受け付ける。** かつ PUT は部分更新で、省略すれば保持され、空文字を
明示的に送れば消える。つまり ZaimViewer から、Zaim の UI では表示も編集もできない
品名を書き込むことも、消すこともできてしまう。消した場合、**Zaim 側に復元手段が無い。**

### 生 API で実測したこと（2026-08-18、検証用の明細 3 件を作成して確認、すべて削除済み）

1. **POST に `receipt_id` を送ると保持される。** 公開 API のパラメータ表にも
   MCP サーバのスキーマにも無い未文書のパラメータだが、通る。
   `9900000001` を送ると `4294967295` (= 2^32-1) に clamp されたので、列は uint32。
2. **レシート実体が無くても UI は品名を出す。** でっち上げた `receipt_id`（`4200000000`）を
   付けた明細で、一覧・詳細・編集のすべてに品名が表示され、品目を編集して更新もできた。
   UI の判定は「レシート実体の存在」ではなく **`receipt_id != 0` だけ**である。
3. **PUT で既存明細に `receipt_id` を後付けできる。** `amount` と `receipt_id` だけを送り、
   `date` / `category_id` / `genre_id` / `name` / `comment` は部分更新の保持がそのまま効いた。

採番の実測値: ミラー内の実 `receipt_id` は 1,776,342,049 〜 1,786,961,813 の範囲にある。
2026-08-01 17:46 の `1785573859` と 2026-08-09 13:36 の `1786250188` の差から、
Zaim の採番速度は約 8.6 万/日。

## 決定

**1. 品名を編集できるのは `receipt_id != 0` の明細だけとする。**
ZaimViewer の編集フォームは Zaim と同じ出し分けをし、`receipt_id = 0` の明細では
品名欄を出さず、PUT のボディにも `name` を含めない。表示（一覧・詳細シート）は
`receipt_id` に関わらず続ける。

`ZaimClient` の更新系メソッドでは、これを型で強制する。`amount` を必須引数にするのと
同じ層で塞ぐ:

```ts
export type PaymentUpdate =
  | (PaymentUpdateBase & { itemized: true; name?: string })
  | (PaymentUpdateBase & { itemized: false; name?: never });
```

**2. 既存の孤児 1,140 件（payment + income）には `receipt_id` を後付けして解消する。**
delete → create の再作成ではなく、in-place の PUT で行う（[#37](https://github.com/Ries630/ZaimViewer/issues/37)）。
`id` も `created` も口座もタグも動かず、変わるのは `receipt_id` が 0 から採番値になることだけ。

**3. 採番は未使用域からの連番（`4200000000 + n`）とし、1 明細 = 1 レシートで振る。**
uint32 上限まで約 9,497 万の余裕があり、1,140 件には十分。Zaim 側の採番が 42 億に
達するのは実測 8.6 万/日から約 77 年先で、衝突は実用上考えなくてよい。

transfer 3 件（すべて「Amazonギフトカード チャージタイプ」4,000 円）は対象から外す。
transfer の PUT 自体を検証しておらず、Zaim の振替画面に品名欄があるのかも
確認していないため（未検証）。

## 検討した代替

### 品名の扱い

- **`receipt_id` を見ずに品名を編集可能にする** — 実装は最も単純。落としたのは、
  2 方向の事故がどちらも一番軽い編集（「メモだけ直す」）で踏めるため。
  (a) 初期値の入れ忘れや空欄保存で `name` が消え、**Zaim の UI からは再入力できない**。
  (b) `receipt_id = 0` の明細に品名を書き込むと、ZaimViewer でしか見えない値になる。
  後者は Zaim の列を使いながら実質的にローカル独自データを作る形で、
  [ADR-0002](0002-no-local-only-data.md) の「Zaim が唯一の正」から外れる
- **品名を全面的に読み取り専用にする** — 事故は起きない。落としたのは、
  実測 2 により `receipt_id != 0` の明細は Zaim の UI でも正規に編集できると分かったため。
  Zaim にできることを ZaimViewer にできなくする理由が無い

### 孤児 1,143 件の扱い

- **放置する（表示だけ続ける）** — 追加作業がゼロで、集合は増えないので実害も広がらない。
  落としたのは、実測 3 により in-place の PUT で解消できると分かり、代償がほぼ無くなったため。
  放置すると「品名が編集できる明細とできない明細が混在する」状態が恒久的に残り、
  編集フォームの出し分けを説明し続けることになる
- **delete → create で再作成する** — 実測 1（POST が `receipt_id` を受け付ける）だけで
  実現できるので、実測 3 の前はこちらを想定していた。落としたのは、明細 `id` と
  `created`（登録日時）が変わるため。実測 3 で PUT による後付けが通り、
  何も失わない経路が見つかった時点で採る理由が消えた

### 採番

- **既存の `receipt_id` を再利用する / 実採番域に続けて振る** — 落としたのは、
  本物のレシートと混ざり、将来 Zaim 側の採番が追いついたときに衝突するため。
  実採番域（17.8 億）から十分離した未使用域を使う

## 結果

- **未文書の API パラメータに依存することになった。** `receipt_id` は Zaim の公開 API の
  パラメータ表に無い。Zaim 側が受け付けなくなれば、移行スクリプトは失敗し、
  移行済みの明細も（Zaim が値を無視するようになれば）品名が再び編集できなくなる
- **`receipt_id` が「実際にレシートだったか」を意味しなくなる。** 移行後の 1,140 件は
  レシート実体を持たない。将来 `receipt_id` でグループ化した合算表示を作る場合、
  この列は「品名を編集できる印」でしかなく、レシートとしての意味を読み取ってはいけない
- **`4200000000` 以上の帯を自作の採番に予約した。** 今後この帯を別の用途に使えない
- **transfer 3 件は品名が読み取り専用のまま残る。** 検証していないので移行対象に
  できず、「品名を編集できる明細とできない明細の混在」を完全には解消できない
- **移行前は 1,140 件の品名が ZaimViewer からも編集できない。** 決定 1 の規則が先に効くため、
  [#37](https://github.com/Ries630/ZaimViewer/issues/37) を実施するまでは読み取り専用が続く
- **`receipt_id` を `/api/transactions` のレスポンスに載せる必要が出た。** 編集フォームの
  出し分けに使うため。[ADR-0029](0029-detail-bottom-sheet-as-edit-entry.md) の時点では
  「ミラーにはあるが API が返していない」列だった

## 再評価のサイン

- **移行スクリプトの dry-run 後の 1 件目で `receipt_id` が保持されなかったとき。**
  Zaim 側の仕様変更を意味するので、決定 2・3 を取り下げて「放置」に戻す
- **移行済みの明細で Zaim の UI に品名が出なくなったとき。** 同上
- **transfer の PUT と振替画面を検証したとき。** 品名欄があるなら 3 件も移行対象に加える
- **Zaim 公式が品目なしの明細でも品名を表示・編集するようになったとき。**
  移行そのものが不要になり、決定 1 の出し分けも要らなくなる
- **Zaim の採番が 40 億に近づいたとき。** 実測 8.6 万/日では約 70 年先だが、
  採番方式が変われば早まる

## 置換理由

支出の編集画面で確認した `receipt_id` の効果を、未検証の収入にも一般化していた。
支出だけに限定し、収入へ後付けした値を戻す判断は
[ADR-0035](0035-itemized-receipt-id-is-payment-only.md) に記録する。
