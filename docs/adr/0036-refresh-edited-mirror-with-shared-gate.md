# ADR-0036: 編集後の再取得結果をミラーへ反映し、同期と共通の排他を使う

- ステータス: 承認済み
- 日付: 2026-09-05
- 関連: [#6](https://github.com/Ries630/ZaimViewer/issues/6)、[#73](https://github.com/Ries630/ZaimViewer/issues/73)、[ADR-0003](0003-edit-through-zaim-api.md)、[ADR-0012](0012-table-swap-sync.md)

## 背景

Zaim へ保存しただけでは一覧のミラーが古いままになる。全件同期はローカルで実行され、
取得済みデータを別テーブルへ構築してから差し替える。取得と差し替えの間に編集が入ると、
その編集より古い値でミラーを上書きする競合がある。

## 決定

Zaim の更新後に再取得して照合した明細だけを、通常列と `raw` を同時にミラーへ反映する。
全件同期の開始から差し替え完了までと編集を、D1 の独立した処理管理テーブルで排他する。
処理管理テーブルはミラーの差し替え対象に含めない。家計データの正は引き続き Zaim である。
`synced_at` は全件同期の時刻として維持する。

排他の取得は単一の条件付き SQL、解除は所有者 ID の一致で行う。期限経過を理由に実行中の
所有者を自動で置き換えない。結果不明またはミラー未反映の編集があれば同期を保留する。
強制終了で所有者が残った場合の復旧手順は [編集の運用手順](../../ops/editing.md) を正とする。

## 検討した代替

- 毎回全件同期を促す: 保存しても iPhone だけで最新の表示へ戻れず、ローカル実行が必要になる。
- クライアントキャッシュだけ変更する: 再読み込みで古いミラーに戻り、同期との競合も残る。
- メモリ上の排他: Worker の複数インスタンスとローカル同期の間で共有できない。
- 期限切れの排他を自動取得する: 先行する外部更新の完了が不明なまま後続更新を許す。

## 受け入れた代償

処理管理テーブルの初期化と異常終了後の復旧が必要になる。読み取りは継続できるが、
結果不明の処理がある間は保存と同期を保留する。Zaim アプリからの同時編集を原子的に
排他する仕組みは確認できておらず、更新直前の変更検出と更新後の照合で検出する。

## 再評価の条件

Zaim が条件付き更新を提供したとき、または排他待ちが継続的に操作を妨げるとき。
