# ADR-0023: 収入の金額のため、light テーマの success だけ値を上書きする

- ステータス: 承認済み
- 日付: 2026-08-12
- 関連: [ADR-0022](0022-daisyui-for-form-components.md)（決定 3 をここで部分的に置き換える）、[#14](https://github.com/Ries630/ZaimViewer/issues/14)、`4fa55db`

## 背景

[ADR-0022](0022-daisyui-for-form-components.md) の決定 2 に従い、パレット直書き
22 箇所を semantic トークンへ置き換えた。決定 3 では「色の値そのものは今決めない。
組み込み `light` の既定のまま進める」としていた。

置き換えたあと、Chrome を iPhone 幅（430×932）にして白地に対するコントラスト比を
測った。Playwright MCP から canvas 経由で sRGB に落とし、WCAG 2.1 の相対輝度の式で
計算している。

| 用途 | 置換前 | 置換後 |
|---|---|---|
| 支出の金額 | `gray-900` 17.75 | `base-content` 17.72 |
| **収入の金額** | `emerald-700` **5.36** | **`success` 1.96** |
| 振替の金額・文脈 | `gray-500` 4.84 | `base-content/60` 4.66 |
| 補足 | `gray-400` 2.60 | `base-content/50` 3.40 |
| 総額 | `gray-600` 7.56 | `base-content/70` 6.57 |
| 「予定」バッジ 文字/地 | 5.09 | `badge badge-info` 6.34 |
| 「予定」バッジ 地/白 | 1.15 | `badge badge-info` 2.22 |
| 「同期が古い」文字/地 | 6.36 | `bg-warning` / `text-warning-content` 5.24 |
| popover 文字/地 | 17.7 | `bg-neutral` / `text-neutral-content` 15.68 |

**収入の金額だけが 1.96:1 になり、読めない。** 組み込み `light` の
`--color-success` が `oklch(76% 0.177 163.223)` で、`bg-success` の地色として使い
`success-content` を上に乗せる前提の明るさだったため。グレーの段階は
`gray-500 → /60`、`gray-400 → /50`、`gray-600 → /70` の対応がいずれも 0.2 以内に
収まり、補足だけは 2.60 → 3.40 と読みやすい方向に動いた。

暗くする候補も同じ手順で測った（色相は組み込み `light` の 163.223 のまま）。

| 明度 | 白地とのコントラスト |
|---|---|
| 45% | 6.70 |
| 50% | 5.47 |
| **52%** | **5.05** |
| 55% | 4.49 |
| 60% | 3.68 |
| 65% | 3.05 |

## 決定

`light` テーマの `--color-success` を `oklch(52% 0.13 163.223)` に上書きする
（5.05:1。置き換え前の `emerald-700` は 5.36:1）。`--color-success-content` も
対で `oklch(98% 0.014 163.223)` に明るくする。JSX は `text-success` のまま変えない。

**上書きするのは success だけ**で、他の色は組み込み `light` の既定のまま置く。
「予定」バッジが淡い水色からべた塗りの水色に変わった点も、文字/地が 5.09 → 6.34 と
読みやすい方向に動いているので `badge badge-info` のまま据え置いた。

## 検討した代替

- **JSX を `text-success-content` にする** — テーマの上書きが要らず、白地に対して
  9:1 前後になる。落としたのは、`success-content` が「`success` の地色の上に乗せる
  文字色」であり用途が逆だから。ダークモードを入れたとき、暗い地に暗い緑が乗って
  破綻する。ADR-0022 が semantic トークンに寄せた目的（テーマを差し替えられる状態を
  作る）を、その場しのぎで崩すことになる
- **色を既定のままにして、色以外で収入を区別する**（先頭の `+` 記号と太字） —
  テーマの色を 1 つも決めずに済む。落としたのは、明るい緑が白地でほぼ判別できず、
  色が意味を持たない飾りとして残るため。金額は一覧で最も目を通す列で、そこを
  読めない色にする理由が無い

## 結果

- **組み込み `light` の success をそのまま使う状態には戻れない。** テーマを増やす
  なら、そのテーマの success を「白地（またはそのテーマの `base-100`）の文字として
  読めるか」で毎回検証することになる。DaisyUI の既定値をそのまま信用できるのは
  他の色だけになった
- **淡い成功色の面が要るときは自前で作ることになる。** `bg-success` の地色が
  `emerald-700` 相当の濃さになったので、成功トーストのような淡い面が欲しければ
  `success/15` のような不透明度の指定で組む
- **semantic トークンで書いても、テーマの既定で読めるとは限らない**ことが分かった。
  トークンを新しく使うたびにコントラストの実測が要る。これは lint でも型でも
  防げず、ADR-0022 の「パレット直書きを混ぜない」と同じくレビューで見るしかない
- ADR-0022 の決定 3「色の値そのものは今決めない」は、success については
  ここで決めたことになる

## 再評価のサイン

- **ダークモードを入れるとき。** 暗い地では明るい success の方が読めるので、この
  上書きは `name: "light"` に閉じている必要がある。テーマを足すときにここが
  漏れると、暗い地に暗い緑が乗る
- **収入以外で success を使い始めたとき。** とくに `bg-success` を使うとき、
  地色が濃い緑であることが前提になっているか確かめる
- **DaisyUI が組み込み `light` の success の値を変えたとき。** 上書きが不要に
  なるかもしれない
